The Rust references below are the committed blobs at RustSHT `91c2cb8ff1ce576bd6dfa6764fd7fb516a00295a`, not the dirty working-tree versions. The compared Rust blob IDs are `transform.rs` `5573ec07a27ec59a9768ec5985884d3ebbdb99f1`, `scalar_paired.rs` `484d910f738ab97e5a9048381ee3cb28ac2532f5`, `scalar.rs` `e9be7a81022d4d2f0bbd30ba0833344309e6f4e9`, and `spin_transform.rs` `736064e9d0505326663b1565204a36d822c87316`. The worktree contains later uncommitted scalar-kernel and profiling changes; they were not used for this source comparison. No code was built or run. The comparison covers the Legendre stage. DUCC `alm2leg` writes ring/order Legendre data; Rust scalar synthesis accumulates Fourier spectra and then performs its inverse longitude FFT in `synthesis_into` (`src/transform.rs:651–660`). Their whole-operation timings therefore include different surrounding stages.

## Source comparison

| Work | Pinned DUCC behavior | RustSHT behavior and work difference |
|---|---|---|
| Order scheduling and storage | `allocate_leg` selects a theta-contiguous underlying layout for parallel synthesis by allocating `{component, order, theta}` and returning its transposed view (`ducc/src/ducc0/sht/sht.cc:566–574`). `alm2leg` uses `execDynamic(nm, nthreads, 1)` and workers repeatedly take order ranges (`:684–719`, `:729–749`); each order is prepared and processed across ring batches before the worker takes another order. | `synthesis_into` divides spectra into disjoint contiguous ring groups and pairs each group with worker recurrence scratch (`src/transform.rs:567–621`). Each `synthesize_ring_group` then walks `m=0..mmax` serially (`:764–786`). This exposes ring-group parallelism, while each worker carries out the full order loop. DUCC exposes dynamic order parallelism. These are different work partitions, not evidence that either is universally cheaper. |
| Scalar coefficient preparation | `inner_loop_a2m` transforms the scalar coefficients in place once for the order (`ducc/src/ducc0/sht/sht_inner_loop.h:1524–1542`), then applies those coefficients while traversing the order’s ring batches (`:1552–1594`). | Each Rust ring-group invocation fills factors and prepares paired scalar coefficients inside its per-order loop (`src/transform.rs:786–818`). Thus the same order’s paired coefficient preparation is repeated across ring groups. On the general paired visitor fallback, the even/odd coefficient expressions are inside the callback (`:914–966`, `:969–1024`); the visitor invokes callbacks over latitude blocks of `LATITUDE_BLOCK_SIZE` (`src/legendre/scalar_paired.rs:2835–2880`). That fallback repeats the coefficient expressions per degree pair and latitude block. This is a concrete possible source of work multiplication; its time share must be measured before changing it. |
| Recurrence setup, scaling, and ordinary kernel | `init_lambda` initializes the sectoral state for vectorized ring lanes (`ducc/src/ducc0/sht/sht_inner_loop.h:413–424`). `iter_to_ieee` advances and rescales lanes until ordinary arithmetic is usable (`:426–456`). `calc_alm2map` handles any remaining scaled prefix, restores ordinary values, then calls `alm2map_kernel` (`:542–590`). The ordinary kernel accumulates coefficients while advancing the same recurrence; wide SIMD has an eight-degree loop, followed by four-degree and tail loops (`:458–540`). | Rust also has scaled initialization and normalization: `sectoral_value` uses scaled powers, while `normalize_pair_lanes` preserves scaled state when ordinary values are unsafe (`src/legendre/scalar.rs:277–318`). The paired block selects an ordinary SIMD kernel when all lanes are normal (`src/legendre/scalar_paired.rs:286–317`, `:1982–2084`); mixed lanes can be compacted for that kernel while scaled lanes continue through the visitor (`:320–387`). The staged transition has a separate safety check and transactional scratch (`:803–897`). The inspected code does not indicate a missing recurrence algorithm; the paths mainly differ in how coefficient work, lane checks, and ring work are grouped. |
| Active rings and reflected output | `fill_a2m` gathers only rings whose order limit permits the current `m`, stores ring indices and weights, pads the SIMD tail, and initializes the recurrence for that packed batch (`ducc/src/ducc0/sht/sht_inner_loop.h:1383–1424`). `extract_a2m` combines the two recurrence sums for reflected rings and applies weights (`:1426–1450`). | Rust handles ring limits inside each ring group. Entirely inactive blocks are skipped; mixed blocks may be compacted and scattered, while other loops check the limit per lane (`src/transform.rs:825–835`, `:899–1024`, `:1045–1075`). DUCC spends work gathering/scattering each order’s active rings to make active lanes dense. Rust’s block-local handling preserves ring-group ownership and avoids building one order-wide packed ring list. A useful comparison is the actual active-lane density and compaction cost, not simply branch count. |
| Spin conversion and two channels | For most high-bandlimit spin-1 rings away from the poles, `alm2leg` splits fast and near-polar ring sets (`ducc/src/ducc0/sht/sht.cc:648–657`). In the fast set it converts spin coefficients with `spin1to0`, normalizes them, then calls scalar `inner_loop_a2m` for each component in sequence (`:684–718`). The near-polar set retains the direct spin path. That path initializes both spin recurrences (`sht_inner_loop.h:686–728`), advances/scales both in `iter_to_ieee_spin` (`:730–771`), and accumulates their contributions in `calc_alm2map_spin` and `alm2map_spin_kernel` (`:773–985`). | Rust’s spin-1 path converts E/B to two scalar coefficient rows per order; q8 may use an order-coefficient cache, otherwise conversion happens in the ring-group worker (`src/spin_transform.rs:1084–1120`, `:1242–1305`, `:1481–1505`). The eligible scalar route prepares both channels and attempts a shared paired block (`:1751–1816`); fallback can execute two prepared scalar blocks (`:1823–1905`), then a visitor uses one basis traversal to form both channel contributions (`:2039–2079`). Thus Rust can share recurrence work across Q/U in its paired and visitor paths, while DUCC’s fast spin-1 conversion runs two scalar channel loops sequentially. The direct spin recurrences remain in both implementations for their applicable near-polar/unsafe routes. |

## Bounded test hypotheses

1. **C1 — order setup duplication.** Add test-only counts and CPU timers for `fill_paired_scalar_factors` and `prepare_paired_scalar_synthesis_coefficients`, split by transform order and ring group. The source predicts one preparation per order per Rust ring group, compared with one DUCC in-place scalar conversion per order before its ring-batch loop. If setup is a material share, an isolated order-owned task that prepares once and consumes multiple ring groups could reduce that work; it may also reduce ring-level parallelism. Screen whole-transform scalar synthesis at T1023 and T2047, with T511 and spin-1 controls. This is distinct from the rejected P02 experiment, which targeted coefficient reuse in the scaled visitor fallback; it is not a recommendation to retry that candidate.

2. **C2 — active-lane utilization.** Record per-order active-ring counts, compacted-block counts, and time in compaction/scatter versus recurrence for Rust, then compare with DUCC’s packed `fill_a2m` batches. The falsifiable prediction is that Rust spends measurable time processing mixed blocks with low active-lane density for high orders. Only if that is observed should an isolated active-ring packing change be screened; keep the existing ring-group scheduler and recurrence arithmetic fixed. Compare scalar T1023/T2047 q1/q8 synthesis and spin-1 T1023/T2047 controls, and retain the current DUCC numerical limits. Both hypotheses are diagnostic first. Existing route profiles identify the scalar visitor as a large cost at T1023/T2047, but they do not yet separate order-coefficient setup or active-ring compaction from visitor recurrence time. No threshold/prefix skipping or new recurrence is proposed here.
