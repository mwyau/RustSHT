# DUCC setup comparison — GL T720 scalar f32

This accuracy/setup-only probe compares the isolated native-generic Rust
candidate with the pinned DUCC 0.42.0 f32 transform API. It does not run a
whole transform, establish independent accuracy, or measure performance.

## Findings

The Rust and DUCC GL T720 latitude arrays, f64 sine, f64 cosine, and f64
cosine-squared values are bitwise identical for all 720 rings. The candidate's
f32 sine and cosine are the correctly rounded f32 values of DUCC's f64 values.
The candidate's normal nonzero-order f32 cosine-squared path differs from the
rounded DUCC value by at most two f32 ULP; its maximum relative difference is
`1.43e-7` and RMS relative difference is `4.82e-8`.

For 968 order-degree pairs (`m=1–16`, `l=600–720`, pair parity preserved),
the candidate's actual `prepare_order` alpha, A/B recurrence factors, and
stored epsilon factors equal the nearest f32 rounding of DUCC's double values.
The actual prepared f32 even and odd coefficient pairs, generated from the
same deterministic f32 high-degree input, differ from DUCC's double-prepared
pairs by relative L2 `3.97e-8` and `3.61e-8`, respectively. F32 pair
preparation is not bitwise the narrowing of DUCC's double result because the
multiply/add operations round in f32.

The earlier one-at-a-time geometry sensitivity (`9.00e-4` relative RMS) and
factor sensitivity (`1.51e-4`) are therefore precision sensitivities of a
high-degree recurrence, not evidence that the Rust GL angles or recurrence
factor formulas differ from DUCC. Small input rounding can be amplified by
the recurrence. The probe's coefficient-pair L2 values are not end-to-end
transform errors.

DUCC's f32 API is a mixed-precision reference for this comparison: its scalar
Legendre path stages coefficients in `complex<double>`, prepares `Ylmgen`
tables in double, and uses `native_simd<double>` recurrence state. It narrows
the Legendre output to f32 before the longitude stage. This comparison does
not justify using a double computational backend in Rust; the Rust candidate
remains native f32 at runtime.

The candidate source base is `b6a96aa7161a64f678b614d73478496f50f0551e`; the
exact isolated source diff is `cc72cbc20048affbdbd6cdbce619af79edc65896a9a0ed9730006179ea3ce7a8`
and is retained as
[`candidate-native-generic.patch.gz`](candidate-native-generic.patch.gz).
The temporary test-only dump patch is
`39aea691deb331e3bef0d69e9a732f6eacf9164414b0930cb0032b8efa4d7f9c` and is
retained as [`actual-pair-preparation-dump.patch.gz`](actual-pair-preparation-dump.patch.gz).
The reference source is DUCC 0.42.0 commit
`42ce8ab5c5d79e0e2fd9af4a09c2ea4693520e1b`.

`ducc_setup.cpp` instantiates DUCC's actual `GL_Integrator`, `YlmBase`, and
`Ylmgen::prepare`, then evaluates the coefficient-preparation expression used
by `inner_loop_a2m`. `rust_setup_probe.rs` reads the candidate's public
`GridSpec` and emits the corresponding f64 and native-f32 geometry. The
`RPAIR` records were emitted from the candidate's actual `prepare_order`
inside the ignored recurrence diagnostic after applying the test-only patch.
The paired input is generated by that test: real f32 values for degrees
600–720 and zeros below degree 600.

See [`command-provenance.txt`](command-provenance.txt) for toolchain, build
commands, and binary hashes. The raw compact inputs are in [`data/`](data/),
and [`compare_setup.py`](compare_setup.py) regenerates
[`results/setup-comparison-summary.json`](results/setup-comparison-summary.json).
Checksums for every file are in [`SHA256SUMS`](SHA256SUMS).
