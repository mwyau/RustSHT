## Dispatch and work layout

For exact GL T720 full-mmax q8 (`ntheta=721`, `mmax=720`), the current source cannot take `hemisphere::synthesize`: `spin1_hemisphere_worker_count` ends at `lmax=511`. At capacity 8, workspace ring groups are 64 rings; the GL T720 spin-1 fine-group selector returns 32, so both values are below 721. The spin-1 coefficient-cache gate checks the workspace value, while the ordinary ring route would use 32; the following order-major route supersedes those groups. Its eligibility count is `ceil(721/8)=91`, above the required 16, and its task tile is one order (`SPIN1_ORDER_MAJOR_TILE=1`). Each queued call therefore has `ring_start=0`, `ring_end=721`, `order_start=m`, `order_end=m+1`, and compact `spectrum_len=1`.

That one-order GL/full-mmax shape satisfies `prepared_component_attempted` in the fast scalar segment: the contiguous-order predicate does not require q1, and the full-grid symmetry condition is `0+721=721`. The call first converts the E/B order into two scalar coefficient rows, checks finiteness, then `try_synthesize_spin1_prepared_component_order_from_workspace` checks input range/subnormal safety and prepares pair coefficients. On acceptance, the reflected adapter runs one scalar SIMD recurrence per output component over northern latitudes and reconstructs both hemispheres. Polar and any declined work stay on the established fallback. Existing test-only route counters resolve the earlier coverage uncertainty: for the deterministic exact-GL T720 fixture, q1 and q8 each attempted and accepted all 721 orders, with zero adapter declines.

The T720 coefficient-row estimate is 16,657,984 bytes. Since it exceeds the 4,000,000-byte local-conversion threshold, this route converts each order into worker-local coefficient rows instead of building the whole table. It also misses the 16,000,000-byte fused-local-preparation gate. The exact q8 one-order shape meets the other fused-preparation conditions; the byte gate excludes it by 657,984 bytes. The existing `spin1_to_scalar_order_with_prepared_pairs` visitor combines conversion, safety checks and pair preparation, but still calls the generic converter and retains its full-row clear. `spin1_to_scalar_with_visit` clears both complete `(lmax+2)` rows for every order, then writes every slot from `m` through `lmax+1`; the prepared adapter and paired fallback consume only that suffix. This makes the repeated full-row clear a source-derived candidate for removal on the order-local route, up to 16,657,984 explicit bytes written per T720 transform. The shared converter may still need its zero-prefix contract elsewhere, so a scoped no-clear variant would have to verify all local fallback consumers and poisoned-scratch behavior. The ordinary order-local route also scans the converted rows for finiteness, then scans the active suffix for safe magnitude/subnormal values; `input_value_is_safe` repeats the finite predicate. A combined status scan could retain both safety boundaries and avoid overlapping finite work. These gate, byte and predicate counts are source-derived; the exclusive Ir/runtime costs of fused preparation, scans and clears are unresolved.

At the exact parent, each of the 721 queued orders cleared two 721-element complex worker rows before the recurrence, then scattered Q/U values to unique columns of ring-major spectra. The clear pass is 16,634,912 bytes and the scatter pass is the same: about 33.27 MB of explicit clear-plus-scatter stores per T720 transform, apart from recurrence writes and the transform's initial spectrum reset. The current candidate removes the eager full-row clear only when a prepared component pass succeeds; it zeros the fallback slices that will use `+=`, while unattempted, declined, skipped and other fallback cases still initialize the full row. The scatter remains. These byte counts are source-derived; no elapsed-time share or cache cost has been measured.

## Existing q8 evidence and limits

The later exact-T720 route profile records 2,280 Q/U component-batch calls, 387,970 active lanes (390,016 vector lanes after padding), 80,941,566 active lane×degree-pair×component updates (81,294,056 padded updates), zero checked/scaled-prefix updates, and 118 generic polar fallback blocks covering 73,584 lane-pair updates. Thus the dominant nonpolar work is the prepared reflected-component ordinary route at both q1 and q8; scaled recurrence is not a likely T720 synthesis target. These are fixture-specific route counts, not a parity result.

The existing one-transform Callgrind profiles report Rust process totals of 560.144M/594.663M Ir and DUCC totals of 525.074M/524.262M Ir at q1/q8. Those boundaries include plan/workspace/thread setup and are not transform-exclusive. Within them, the inlined Rust ordinary-component callback source contexts sum to 250.617M Ir (44.7% q1, 42.1% q8), while DUCC `alm2map_kernel` is 302.305M Ir (about 57.6% at both q). Normalizing these hot-route sums by the recorded padded work gives about 3.08 Rust Ir/update versus 3.72 DUCC Ir/update; the differing callback/function boundaries make this directional, but it does not support a claim that Rust performs more ordinary-loop instructions per useful update. Subtracting these selected totals from the whole-process totals leaves a nominal +122.1M Rust Ir outside the selected groups, while the net process gap is +70.4M; the selected scopes are not fully equivalent, so that residual is an unresolved boundary/setup bucket rather than an exclusive attribution. `iter_to_ieee` is 3.259M Ir (0.55% of Rust q8 process Ir), and the route counters show no checked/scaled updates.

The existing matched parent/candidate Callgrind comparison isolates the WIP's whole-program effect. Parent/candidate totals were 560,143,992/560,166,719 Ir at q1 (+22,727, effectively unchanged) and 594,662,809/580,848,633 Ir at q8 (−13,814,176, −2.323%). DUCC totals were 525,074,155 q1 and 524,261,883 q8. The q8 candidate's inclusive `synthesize_spin1_order_major_queue` count fell from 521,650,553 to 507,879,183 Ir (−13,771,370); this is inclusive attribution, not the exclusive cost of the removed fills. The q1 route does not use that queue, explaining why the candidate is neutral there. These one-transform Callgrind boundaries include process setup. The q8 instruction reduction is candidate evidence, not an elapsed-time claim or performance acceptance.

The existing optimized AVX2 disassembly shows no missed hot-loop inline boundary. The Rust loop at `0x17ceeb..0x17cfdb` has 45 static instructions, 24 YMM FMAs, 12 scalar broadcasts and one loop branch for two degree pairs over two vectors. Its branch PC is entered 4,981,112 times at each q; 12 broadcasts per entry yield 59.77M executed broadcasts. The first `cos(theta)^2` vector is loaded from packed geometry at `0x17ce4f`, stored to `[rsp+0x70]` at `0x17ce54`, and reloaded twice per iteration at `0x17cf4c` and `0x17cfb5`; this is a compiler spill of one invariant geometry vector, not application scratch access. Recurrence values and four accumulators remain in vector registers. The loop contains no call. DUCC's `alm2map_kernel` body at `0x67c900..0x67c9b5` has 42 static instructions, 12 YMM FMAs and one loop branch for two degree pairs over one vector. Its inner loop is entered 9,934,482 times; 12 coefficient broadcasts occur in the setup block across 235,410 batch invocations (2.82M total), before the latitude-vector loop. DUCC spills three coefficient vectors to stack, then reloads those three inside each vector iteration; recurrence state is intentionally array-backed and loaded/stored per iteration. Both kernels therefore have stack traffic, but for different values and dataflow. Both execute 1.5 YMM FMAs per normalized lane-pair update. Although Rust broadcasts coefficients more often, the matched hot-route instruction proxy is lower for Rust (3.08 versus 3.72 Ir/update); those broadcasts are not by themselves a demonstrated whole-program cost to remove. Loop interchange would also exchange register-held recurrence state for longer live ranges or state memory traffic, so it remains unsupported without a bounded kernel comparison.

`PreparedComponentBatch::with_simd` computes `power_lower_limit(m)` for each component batch. The dispatcher retains the corresponding `exp@GLIBC` call; the existing q8 Callgrind profile attributes 129,732 Ir to all such `exp` children, about 0.022% of the full process total. There are 2,276 nonzero-order calls among the 2,280 Q/U component batches (order zero returns before `exp`), so repeated threshold work is real but too small to prioritize. SIMD dispatch itself occurs once per batch; the recurrence loop has no helper calls, so adding more `inline` attributes is unsupported by this evidence.

The accepted historical Plan 16 order-major experiment on exact GL T720 full q8 reported Rust 19.509 ms on the old group route, 15.199 ms after order-major dispatch, and DUCC 5.903 ms (2.58× for the new route on that dated build). Its phase probe put Legendre recurrence plus spectrum work at 19.678→12.579 ms; summed worker factor preparation fell 13.518→1.330 ms, cache preparation was 1.883→1.885 ms, and FFT/writeback was 1.318→0.929 ms. These are route-history results, not current performance evidence: the latest [PERFORMANCE_STATUS.md](../PERFORMANCE_STATUS.md) separately lists a later historical GL T720 q8 snapshot near 0.95× DUCC, also uncertified at current HEAD. The differing dated results are not combined; current-HEAD GL T720 q8 parity and phase attribution remain unmeasured.

The source-matrix GL T320 oversampled spin-1 q8 profile recorded 605.134M Rust Ir and 226.425M Ir for a different DUCC source build. DUCC `alm2map_spin_kernel` was attributed 110.741M Ir (48.9% of that DUCC total); Rust's q8 report gives unchanged top AVX2 helper counts across the inlining candidate but no work-normalized Rust-exclusive kernel split. That route used grouped-ring recurrence, had no active-work normalization, and did not change under the scalar ordered inlining candidate. It cannot establish T720 exact-q8 costs. Conversely, exact GL T720 q8 can attempt the prepared-component adapter, so the T320 result does not show that this route misses the SIMD-inline boundary.

For GL T320 oversampled q8, the present f64 scheduler has a concrete coarse-grain concern. With `LATITUDE_BLOCK_SIZE=128`, 640 rings produce five base blocks; the workspace grouping rule halves the one-block group to 64 rings, giving ten groups. The fine-group exception is exact-GL-only, the coefficient-cache/dynamic-queue gates are false, and f64's `prefers_fine_spin1_synthesis_groups()` default is false. The static iterator consequently uses `with_min_len(ceil(10/8)) = with_min_len(2)`, which permits at most five Rayon leaves for ten items. This is a **source-derived upper bound on simultaneously available group tasks**, not proof that only five workers ran: task execution and occupancy need worker evidence. It is a credible q8 scaling hypothesis given the existing 5.7× timing gap, but the source-matrix host was shared and the old profile did not record active workers.

The other q8 group routes also expose bounded task counts: exact CC T360 has six static groups, while oversampled CC T360 has twelve groups with `with_min_len(2)`, permitting at most six leaves. In contrast, exact GL T320's hemisphere path queues 16 groups, and exact GL T720's order-major path queues 721 one-order tasks. The source-matrix screens reported CC T360 exact Rust q8 at 18.709 ms versus q1 19.284 ms (DUCC q8 1.965 ms), and CC oversampled q8 at 18.729 ms versus q1 34.910 ms (DUCC q8 4.014 ms). Those timings are consistent with insufficient q8 task supply contributing to the CC gap, but they do not prove it: there is no worker-occupancy trace, the host was shared, and kernel instruction density also differs.

The same over-resolved ring-group path also repeats order preparation across groups. Its coefficient cache is gated to exact GL, exact CC with more groups than workers, or selected F1; for over-resolved GL/CC the cache is false. Each group then loops over orders and, for orders active in that group, performs `spin1_to_scalar`, fills per-order recurrence factors, and prepares paired coefficients in its worker scratch. Low orders remain active across all ten GL T320 groups (and twelve CC T360 oversampled groups), so the source permits those order-only steps to repeat up to the group count. Polar-order checks skip inactive orders before conversion, so this is only an upper bound, not a count. The accepted T1023 q1 profile (`7ef6d6e1`) attributes 106.379M inclusive Ir (8.85% of total) to `spin1_to_scalar_with_visit`; this shows coefficient conversion/preparation is measurable in that different, once-per-order route, but it does not quantify q8 or over-resolved T320. The matching source-matrix DUCC is `31d9fe99`: for T320/T360 (`lmax < 500`) `alm2leg` takes its normal route, gathers original E/B coefficients once per m, and calls `inner_loop_a2m` for all ring data; it does not call `spin1to0`. For T720's fast-ring route, DUCC calls `spin1to0` once per m, then runs both scalar Legendre components. In both routes, `execDynamic(nm,nthreads,1)` distributes one m-order task at a time. Existing q8 totals (Rust 605.134M vs DUCC 226.425M Ir at oversampled GL T320) do not isolate the repeated Rust work. A later measurement should count coefficient-conversion and pair-preparation calls by order/group; only then consider extending the existing shared coefficient cache or the order-major traversal to over-resolved GL/CC.

For the same GL T320 over q8 route, `synthesize_prepared_scalar_pair_block_dispatched` enters `FusedPreparedSynthesisPairBlock`: its source loop is lane-block outer, degree-pair inner. Pinned DUCC's T320 direct-spin `alm2map_spin_kernel` is degree-pair outer and reuses coefficient vectors across `i<nv2` for each packed batch. This gives a second instruction-level hypothesis beyond repeated order preparation: Rust may reload/re-broadcast coefficient factors per AVX2 lane block, while DUCC does so per batch. Rust fuses two scalar channels and DUCC maintains plus/minus spin recurrences, and Rust's groups cover physical rings while DUCC packs reflected pairs; they do different work shapes. The existing 2,270 fused-block counter and whole-program Ir totals do not quantify this loop-order cost. Dynamic PC counts normalized by active physical/reflected latitude × degree-pair × channel work are still required.

The exact-GL T320 q8 hemisphere path has a different preparation repeat. Its q8 cache gate prepares scalar coefficient rows once, but each of 16 ring groups copies two `(lmax+2)`-element complex rows into worker scratch for every order, then rebuilds paired recurrence coefficients locally. The copies alone are about 52.9 MB one-way per transform (about 105.8 MB of load+store traffic), source-counted for 16 groups and 321 orders; this excludes paired-factor preparation. The bounded-basis SIMD kernel then writes one degree tile and reads it once for each of two scalar-channel accumulations. That scratch reuse limits live accumulators; removing it could restore register spills. The normal path deliberately keeps this scratch worker-owned. Pinned DUCC 0.42.0 does **not** call `spin1to0` for T320: `alm2leg` uses its normal direct spin recurrence when `lmax < 500`, gathers original E/B coefficients once per order, and runs both components through `inner_loop_a2m`. Therefore the copy/preparation difference is a valid Rust source cost, but the direct DUCC recurrence performs different arithmetic; compare equal active lane-pair and degree work before assigning an instruction premium. The source-matrix DUCC revision `31d9fe99` has the same normal/fast split, but that is the revision used by the 605.134M/226.425M q8 profile, not the pinned production binary.

At the other end, exact GL T720 q8 takes the one-order queue and not the ring-group scheduler. Its existing route stages each order through worker-local Q/U rows: clearing and scattering 721 complex values for each of two channels costs about 33.27 MB of explicit stores per transform. The global spectra were already zeroed. This is source-counted traffic, not measured cache or elapsed cost; direct unique-order output would need to preserve zero inactive cells and reset a partially written order before fallback. DUCC's parallel layout is m-major behind a transposed view and its `alm2leg` prepares spin-1 scalar coefficients once per order before its inner recurrence, so the staging difference is plausible but not yet an apples-to-apples store-cost comparison.

The existing scalar inlining change must also be interpreted by route. `PreparedComponentBatch::with_simd`, `synthesize_batch`, and `synthesize_ordinary_suffix_two_vectors` are marked `inline(always)` in the audited source. The T320 oversampled q8 profile shows that this prepared-component kernel is not entered by the grouped spin-1 route: its Ir and top AVX2 helper counts were unchanged by the candidate. The accepted T1023 q1 disassembly reports a direct four-lane YMM ordinary loop with one live coefficient-vector spill, but it does not establish executed q8 PC cost. Do not add another inline attribute without an exact q8 PC and generated-code target.

## Source-only AVX2 comparison for exact GL T720 q8

This is a concrete instruction-count hypothesis, not a measured result. In Rust's accepted GL T720 order-major route, each scalar Q/U pass sees at most 361 reflected northern lanes. `SCALAR_ORDER_BATCH_SIZE=256`, and the ordinary suffix processes two AVX2 vectors per call (`2 * S::F64_LANES = 8` lanes). If the checked prefix reaches ordinary range, a fully active order's two batches therefore traverse the pair loop in at most 32 two-vector chunks for the first 256 lanes, then 13 two-vector chunks plus one final vector for the remaining 105 lanes: at most 46 chunks per component. High-order polar limits reduce this count. Inside each chunk, the degree-pair loop reads the scalar recurrence and even/odd coefficient arrays; `ordinary_two_pair_step_two_vectors` splats each coefficient once and shares it across the two vectors. Source structure therefore permits the same per-degree coefficients to be loaded/broadcast again for each 2-vector chunk; the optimized q8 dynamic PC count is unresolved (`scalar_ordered.rs:962-982, 1122-1248, 2082-2155`).

Pinned DUCC 0.42.0 uses `VLEN=4` for AVX2. On the T720 fast spin-1 route, `alm2leg` applies `spin1to0` once per order and then runs `inner_loop_a2m` for each scalar component. Because `gen.s==0`, that inner loop uses `fill_a2m`, not `fill_a2m_spin`: `nv0=256/VLEN=64`, so each `fill_a2m` batch holds up to 256 compact reflected ring records. `calc_alm2map` then calls `alm2map_kernel`, which loads each degree's coefficient vectors before its `i<nv2` loop and reuses them across up to 64 AVX2 latitude vectors. For T720, `lstep=4096` exceeds the order's degree span, so one recurrence call handles the full degree range per ring-data batch. If all 361 reflected latitude pairs enter the fast route and remain active for an order, DUCC uses at most two 256-record batches per component. The relevant loop nesting differs: Rust's ordinary suffix places the 8-lane chunk loop outside the degree-pair loop, while DUCC places degree outside the `i<nv2` vector loop. Normalized by active SIMD work, both cover 64 vector groups for the first 256 reflected latitude pairs and 27 for the remaining 105 padded to 108: 91 AVX2 vector groups per degree-pair update and scalar component. Rust's 46 helper chunks are 32×2 + 13×2 + 1 vector groups; DUCC's two ring-data batch invocations per component cover 64+27. This does **not** indicate more vector recurrence updates in Rust. The candidate excess is repeated per-degree coefficient loads/broadcasts and chunk-loop overhead: the Rust source splats per two-vector chunk, while DUCC loads coefficient vectors once before its vector-group loop. Actual q8 dynamic counts remain unmeasured; Rust retains recurrence and four sums in registers, while DUCC updates array-backed vector states across larger batches. `rdata_fast`'s sine threshold and order-specific `mlim` can reduce those counts. Register pressure, scratch traffic, cache reuse and LLVM loop transforms must be checked in optimized q8 code before treating repeated splats as removable cost (`sht.cc:190-220, 651-747; sht_inner_loop.h:253-282, 458-545, 1388-1450, 1524-1654`).

A bounded future profile should attribute the coefficient loads/splats and recurrence-state loads/stores separately for the exact q8 adapter, normalize by active reflected-pair × degree-pair × component work, and verify the actual `synthesize_ordinary_suffix_two_vectors` PCs. A possible source-level direction is to reuse coefficient broadcasts across more latitude vectors while retaining only a safe number of live recurrence states; directly widening the current two-vector chunk could spill on AVX2 and is not recommended without disassembly. DUCC's larger batch is an algorithmic reference, not a design to copy blindly.

One tempting redundant operation is already ruled out by prior evidence. The source once placed `cosine * cosine` inside paired loops, but the archived T511 test found the AVX2 compiler had emitted the multiply before the degree-pair loop in both baseline and candidate; static instruction counts matched and moving it in source did not create a repeatable whole-transform gain. Do not repeat that source hoist. The remaining q8 question above is about coefficient-array loads/broadcasts across lane chunks, a separate loop-order mechanism not answered by that earlier disassembly (`archive/experiments/fused-synthesis-register-hoist-2026-10-14.md`).

## Preliminary hypotheses (not production changes or measured rankings)

1. **Exact GL T720 q8 order-local coefficient conversion and validation.** The 16,657,984-byte estimate otherwise satisfies the q8 fused-local-preparation shape but exceeds its gate by 657,984 bytes (4.1%). That existing visitor combines conversion, value safety checks and pair preparation; it could remove the separate row finiteness scan, suffix safety scan and later pair-preparation traversal, although its actual cost is unknown and the threshold may encode a crossover. This fused path was accepted on the distinct CC T720 reduced-q8 workload at 4.18MB, but that result does not establish its crossover at 16.66MB on full GL. It still clears both complete rows first. Independently, the local converter clears 16.66 MB across all orders before overwriting every `m..=lmax+1` slot; the reflected adapter and paired fallback consume only that suffix. A scoped no-clear order-local converter could remove these writes and combine validation while preserving the generic converter contract. Byte/predicate counts have no exclusive Ir or runtime attribution. Any experiment must keep the fallback path and validate poisoned scratch.
2. **Exact GL T720 q8 coefficient broadcasts.** The source layout permits up to 46 Rust 8-lane suffix chunks per component/order versus up to two pinned-DUCC 256-record batches for a fully fast/active order. The existing q8 body disassembly confirms repeated Rust scalar broadcasts and DUCC's pre-loop coefficient-vector loads, but no dynamic PC subtotal isolates their executed cost. It remains a plausible optimization lead, not a supported speedup claim. Reuse across more latitude vectors would expand live recurrence state: the current two-vector path already carries 12 recurrence/accumulator YMM values plus geometry vectors, so a four-vector unroll risks exceeding AVX2's 16 architectural YMM registers. Do not widen or reorder that loop without authorized measurements showing a removable cost and codegen without damaging spills.
3. **Over-resolved GL/CC q8 grouped-route overhead.** The GL T320 over q8 profile has 605.134M Rust versus 226.425M DUCC Ir, and its route counters report 2,270 ordinary fused blocks covering 12.85M lane-pair updates. Source bounds its static schedule to five leaves; CC exact/over-resolved q8 schedules permit at most six leaves. Repeated coefficient conversion and paired-factor preparation are also possible in grouped routes. For GL T320 over specifically, the existing one-order queue is blocked by the cache-geometry predicate requiring exact GL. The scalar-row cache would be 3,287,040 bytes (below the 4,000,000-byte local-conversion cutoff and 34 MiB cache cap); 320 orders produce 40 eligibility tiles, above the q8 threshold of 16. The prepared-component adapter's full-mmax GL predicate already permits the geometry. Existing source-matrix q1 counters report 321 successful adapter orders on both exact and oversampled GL T320; they do not validate q8 order-parallel output or its fallback/reset behavior. ## Source-only optimization shortlist (preliminary)

1. **Keep the current queue-row candidate pending timing.** Its q8 whole-program Callgrind reduction is material enough to justify one matched runtime check; q1 is unaffected. The fallback/reset branches add complexity, so retain only if whole-transform timings support it without cross-workload regression. No more code changes to this candidate are needed during the pause.
2. **Consider suffix-only initialization in `spin1_to_scalar_with_visit`.** The converter clears both full `(lmax+2)` rows, then writes every slot `m..=lmax+1`; current prepared and paired-fallback consumers use that suffix. A narrowly scoped implementation could preserve the existing full-row contract by zeroing only `[0..m]` and any oversized tail, while skipping the suffix clear that is immediately overwritten. Existing Callgrind attributes 16.662M Ir to the two converter clears, an upper bound; the exact removable suffix share is unresolved. This is a source-grounded next experiment, but it still needs focused converter/poison/fallback checks and matched whole-transform Ir/timing.
3. **Defer SIMD widening and threshold hoisting.** Rust's two-vector loop and DUCC's one-vector loop both perform 1.5 vector FMAs per normalized lane-pair update; Rust's ordinary hot-route Ir/update is lower in the existing directional comparison. Coefficient broadcasts repeat across Rust's 8-lane chunks, but their exclusive Ir is not isolated and a wider live state risks AVX2 spills. The repeated `power_lower_limit(m)` threshold is a simple cleanup idea, but its exp children total only 129,732 Ir (0.022% of q8 process Ir), too little to justify added plumbing without timing evidence.
