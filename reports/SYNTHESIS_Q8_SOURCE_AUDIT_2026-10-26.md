# Spin-1 synthesis q8 source and measurement audit

## CPU-exclusive read-only dispatch and SIMD review (PRELIMINARY, 2026-10-26 13:25 UTC)

The current source is unchanged from `97fe394c` (`src/spin_transform.rs` blob `c24d8c24`); `c7421af6` is documentation-only. No profiler, timing loop, benchmark, build, or test ran for this review. The user has reserved the CPU for `sht_bench`; resume measurements only after explicit authorization.

**Clarification on the T320 reduced-q8 queue:** `SPIN1_ORDER_MAJOR_ELIGIBILITY_TILE=8` is used only by the dispatch threshold. With 121 orders, the eligibility calculation is `ceil(121/8)=16`, exactly the minimum for q8. The selected queue has a different task grain: `SPIN1_ORDER_MAJOR_TILE=1`, `fetch_add(1)`, and `order_count=121`, so it claims 121 one-order tasks across eight recurrence workers. The route is at its eligibility threshold, but it is not an eight-task or statically underfilled queue. Queue starvation is therefore not supported by the current source. Dynamic per-order cost skew remains possible but unmeasured.

The same T320 reduced route prepares the two scalar coefficient rows in the shared cache (1,246,784 bytes), then handles each order over the full latitude domain. When paired-factor and coefficient safety checks pass, source permits one reflected-component adapter attempt for that order; a decline after writes clears the order before checked fallback. The current attempt/success/decline counts, polar fallback work, and replay frequency remain unknown. The older over-resolved grouped-route hypothesis of repeated conversion per ring group does **not** apply to this accepted cache/order-queue route.

The strongest supported algorithmic distinction is that T320 (`lmax=320`) remains on DUCC's direct-spin `fill_a2m_spin` / `calc_alm2map_spin` route, while Rust's eligible route converts E/B coefficients to scalar components and runs paired scalar recurrence. This may change useful work and instruction mix, but it is not yet causal evidence: T320 full q8 uses the same broad scalar/order-queue family and beats DUCC (2.104/2.254 ms), while reduced q8 is 1.247× DUCC (1.464/1.176 ms). Reduced whole-worker Ir is only 4.1% above DUCC (816M/784M), and the saved median runqueue wait is 6.94%/0.16%. The different order count and FFT/output shape plus wait imbalance leave the elapsed gap unattributed.

**Inlining and redundant operations:** the exact-T720 q8 reference route has 721/721 adapter orders accepted. Its two-vector ordinary suffix is already forced inline and has no call edge; the one-vector tail is 0.42% of saved process Ir. The saved assembly/profile count of 59.77M Rust versus 2.82M DUCC coefficient broadcasts is not a target by itself: normalized ordinary FMA work/update matches, directional Rust Ir/update is lower (3.08 versus 3.72), and saved Rust elapsed time is 5.561 ms versus 5.885 ms DUCC. A prior inline experiment had no q8 benefit and an adverse q1 screen. Recomputing `power_lower_limit(m)` for each prepared component batch is a source-visible duplicate, but its saved cost is only 0.022% of process Ir. Neither supports another inline attribute, wider live SIMD state, or threshold plumbing.

**Evidence-ranked next hypotheses (not production recommendations):**

1. **T320 reduced q8 recurrence-route cost — medium confidence as a differentiator, low causal confidence.** Recollect current adapter hit/decline and active latitude × degree × component updates, then compare scalar-converted and existing direct-spin kernels while holding the one-order queue and transforms fixed. Simply raising `SPIN1_FAST_MIN_LMAX` would also disable the cache/order queue and confound the comparison; do not change the production threshold from source inspection.
2. **Per-order fallback replay — low confidence.** Count only if the adapter declines after partial writes; the caller explicitly clears and replays through checked fallback. If declines are rare, this cannot explain a whole-transform gap; if common, bucket the decline reason before designing a safe dispatch boundary.
3. **Output/FFT locality and q8 worker tail — low confidence.** The ring-major spectrum scatter and saved runqueue-wait asymmetry are plausible non-recurrence factors, but the same-shape full control passes and no cache/worker occupancy evidence isolates them. Do not add scratch transposes or alter queue ownership without a targeted profile.

**Disposition during the pause:** no source optimization is supported. Keep T320 reduced q8's 1.247× gap open, T320 full q8 as a pass control, and exact-T720 q8 as an inline/broadcast negative control. After explicit measurement authorization, instrument only the current T320 reduced route's adapter outcomes, pair preparation, fallback, and active updates; then compare the existing spin routes at matched scheduling and whole-transform boundaries.

## CPU-exclusive source comparison: remaining GL T320 reduced q8 gap (PRELIMINARY, 2026-10-26 10:57 UTC)

No benchmark, Callgrind, perf, build, or test ran for this comparison. The current production source is `260b74a8`; only documentation changed at the checkout tip. The pause remains active.

The strongest measured residual q8 synthesis gap with a 15-pair result is over-resolved GL T320 reduced `mmax=120`: Rust `1.464 ms`, pinned DUCC `1.176 ms` (1.247x). The matched whole-worker Callgrind boundary is `816M` versus `784M` Ir, only about 4% more Rust instructions. This whole-worker difference does not identify a kernel cause and cannot explain the elapsed ratio on its own. The older T320 source profile described a pre-gate grouped route and used a non-pinned DUCC revision; it cannot be used to attribute the accepted current route.

The accepted gate makes this a distinct dispatch: `ntheta=640 > lmax=320`, q8, and `ceil((mmax+1)/8)=16` meets the order-queue threshold. Its scalar coefficient rows occupy `1,246,784` bytes, below the 4 MB global-cache cutoff. The current source therefore selects the one-order queue with globally prepared scalar coefficients. Its full-domain GL order shape is eligible to attempt the prepared reflected-component adapter, but current T320 reduced adapter hit/decline counts are unresolved. Do not assume all orders use the adapter based on exact T720 counters.

The same-`lmax` GL T320 full q8 control is a useful counterexample: it also satisfies the one-order/global-cache route, but is a measured pass at `2.104 ms` versus DUCC `2.254 ms` (`0.934x`). Reduced T320 changes both the order count (`321` to `121`) and longitude/spectrum shape (`nphi=1280`, `spectrum_len=641` to `nphi=250`, `spectrum_len=126`), while the elapsed ratio moves to `1.247x`. Thus the scalar-versus-direct recurrence boundary alone cannot explain the reduced gap. The smaller route has fewer dynamic order tasks and a much smaller FFT/output problem; those fixed-work, scheduling and phase costs change together and have no current disjoint attribution. Existing whole-worker Ir is `1.717B/1.751B` Rust/DUCC full and `816M/784M` reduced, while the reduced timing record also has unequal median runqueue wait (`6.94%`/`0.16%`). These observations keep the reduced case's timing cause unresolved.

One source-only memory hypothesis is the final order scatter: Rust zeroes each worker's contiguous Q/U rows, phases all rings, then writes one complex value per ring to `ring * spectrum_len + m`; DUCC's parallel synthesis backing is physically order-major with rings contiguous. For reduced T320, 126 complex values make a 2,016-byte ring row, and the one-order atomic queue can assign adjacent order columns to different workers; adjacent 16-byte values can therefore share 64-byte cache lines. This is a possible coherence cost, not measured cache evidence. The explicit row clear plus scatter is about `4.96 MB` per transform for the 121-order reduced case. It is lower than the corresponding full T320 traffic, which nevertheless beats DUCC, so the source layout alone is not a sufficient explanation. Do not add output staging or alter queue granularity without a mechanism-specific profile.

Pinned DUCC 0.42.0 takes a materially different small-degree path. In `sht.cc::alm2leg`, the `rdata_fast` spin route is gated on `lmax >= 500`; T320 instead builds `YlmBase(..., spin=1)` and enters `inner_loop_a2m` with nonzero spin. `sht_inner_loop.h::inner_loop_a2m` then calls `fill_a2m_spin` and `calc_alm2map_spin`; it does not first call `spin1to0`. Current Rust q8 order-queue code prepares E/B-derived scalar rows and may run the reflected scalar-component recurrence. This algorithmic distinction is a concrete hypothesis for matched active-work attribution, not proof that Rust does more work or that a direct-spin Rust route would be faster.

The saved exact-grid T720 q8 profile is a separate control: its selected scalar reflected route has equal reported normal-range FMA work/update against DUCC, lower directional Rust Ir/update, and slightly lower saved elapsed time. Its coefficient-broadcast count cannot be transferred to T320 reduced. The T320 reduced result instead needs current-route counts for coefficient preparation, adapter acceptance/fallback, active reflected pairs, degree-pair updates, and equivalent DUCC direct-spin updates before choosing a code experiment. Existing row-clear and inlining candidates remain rejected/unsupported; no production change is recommended during the pause.

Pinned DUCC's `allocate_leg` uses `(component, order, ring)` backing for parallel synthesis, returned as a transposed `(component, ring, order)` view. `alm2leg` converts spin-1 coefficients once per order with `spin1to0`, then calls `inner_loop_a2m` for each scalar component; `fill_a2m` packs active rings, `calc_alm2map` runs the scalar recurrence, and `extract_a2m` writes results by order. For q8 T720, neighboring order workers can therefore write adjacent complex values in the same cache lines while walking 721-ring-strided streams; DUCC's per-order ring values are contiguous in its backing. This is a source-grounded q8 cache-locality/false-sharing hypothesis, not a measured cost: Callgrind Ir cannot price cache-line ownership, and no hardware-counter or cache-line attribution is available. The row-clear candidate's negative whole-transform result does not measure layout effects. Changing the layout could require a full Q/U transpose or extra scratch, so do not pursue it without new runtime evidence.

The same source dispatch selects the order-major queue for full GL T1023 q8: with eight workers, exact GL geometry enables coefficient caching, `ceil(1024/8)=128` eligibility tiles exceeds the 16-tile gate, the dynamic spin-1 queue is enabled, and `lmax=1023` is at the cache gate's maximum. Its local coefficient-row estimate is 33,587,200 bytes, so the queue uses the order-local conversion route. T720's 721/721 successful-adapter counter does not establish T1023 success coverage: no matching T1023 q8 route counters are available, and high-order polar/safety fallback rates are unresolved. T1023 can require up to two 256-lane batches per northern component pass before polar trimming, so its source path has more degree work per batch and potentially more repeated threshold/broadcast sites than T720; actual q8 update counts and PC costs must wait for authorized profiling.

At T1023 the exact parent clears two 1,024-element `Complex<f64>` worker rows per order and scatters Q/U to the global ring-major outputs; the rejected candidate had deferred that clear on successful prepared-component orders but retained scratch rows, recurrence stores and scatter. Exclusive instruction savings, cache traffic, T1023 fallback rates and elapsed benefit remain unresolved; the rejected T720 result is no evidence for accepting the analogous T1023 change.

The later exact-T720 route profile records 2,280 Q/U component-batch calls, 387,970 active lanes (390,016 vector lanes after padding), 80,941,566 active lane×degree-pair×component updates (81,294,056 padded updates), zero checked/scaled-prefix updates, and 118 generic polar fallback blocks covering 73,584 lane-pair updates. Thus the dominant nonpolar work is the prepared reflected-component ordinary route at both q1 and q8; scaled recurrence is not a likely T720 synthesis target. These are fixture-specific route counts, not a parity result.

The existing optimized AVX2 disassembly shows no missed hot-loop inline boundary in the main two-vector loop. The Rust loop at `0x17ceeb..0x17cfdb` has 45 static instructions, 24 YMM FMAs, 12 scalar broadcasts and one loop branch for two degree pairs over two vectors. For GL T320 oversampled q8, the present f64 scheduler has a concrete coarse-grain concern. With `LATITUDE_BLOCK_SIZE=128`, 640 rings produce five base blocks; the workspace grouping rule halves the one-block group to 64 rings, giving ten groups. The fine-group exception is exact-GL-only, the coefficient-cache/dynamic-queue gates are false, and f64's `prefers_fine_spin1_synthesis_groups()` default is false. The static iterator consequently uses `with_min_len(ceil(10/8)) = with_min_len(2)`, which permits at most five Rayon leaves for ten items. This is a **source-derived upper bound on simultaneously available group tasks**, not proof that only five workers ran: task execution and occupancy need worker evidence. It is a credible q8 scaling hypothesis given the existing 5.7× timing gap, but the source-matrix host was shared and the old profile did not record active workers.

The other q8 group routes also expose bounded task counts: exact CC T360 has six static groups, while oversampled CC T360 has twelve groups with `with_min_len(2)`, permitting at most six leaves. In contrast, exact GL T320's hemisphere path queues 16 groups, and exact GL T720's order-major path queues 721 one-order tasks. The source-matrix screens reported CC T360 exact Rust q8 at 18.709 ms versus q1 19.284 ms (DUCC q8 1.965 ms), and CC oversampled q8 at 18.729 ms versus q1 34.910 ms (DUCC q8 4.014 ms). Those timings are consistent with insufficient q8 task supply contributing to the CC gap, but they do not prove it: there is no worker-occupancy trace, the host was shared, and kernel instruction density also differs.

The same over-resolved ring-group path also repeats order preparation across groups. Its coefficient cache is gated to exact GL, exact CC with more groups than workers, or selected F1; for over-resolved GL/CC the cache is false. Each group then loops over orders and, for orders active in that group, performs `spin1_to_scalar`, fills per-order recurrence factors, and prepares paired coefficients in its worker scratch. Low orders remain active across all ten GL T320 groups (and twelve CC T360 oversampled groups), so the source permits those order-only steps to repeat up to the group count. Polar-order checks skip inactive orders before conversion, so this is only an upper bound, not a count. The accepted T1023 q1 profile (`7ef6d6e1`) attributes 106.379M inclusive Ir (8.85% of total) to `spin1_to_scalar_with_visit`; this shows coefficient conversion/preparation is measurable in that different, once-per-order route, but it does not quantify q8 or over-resolved T320. The matching source-matrix DUCC is `31d9fe99`: for T320/T360 (`lmax < 500`) `alm2leg` takes its normal route, gathers original E/B coefficients once per m, and calls `inner_loop_a2m` for all ring data; it does not call `spin1to0`. For T720's fast-ring route, DUCC calls `spin1to0` once per m, then runs both scalar Legendre components. In both routes, `execDynamic(nm,nthreads,1)` distributes one m-order task at a time. Existing q8 totals (Rust 605.134M vs DUCC 226.425M Ir at oversampled GL T320) do not isolate the repeated Rust work. A later measurement should count coefficient-conversion and pair-preparation calls by order/group; only then consider extending the existing shared coefficient cache or the order-major traversal to over-resolved GL/CC.

For the same GL T320 over q8 route, `synthesize_prepared_scalar_pair_block_dispatched` enters `FusedPreparedSynthesisPairBlock`: its source loop is lane-block outer, degree-pair inner. Pinned DUCC's T320 direct-spin `alm2map_spin_kernel` is degree-pair outer and reuses coefficient vectors across `i<nv2` for each packed batch. This gives a second instruction-level hypothesis beyond repeated order preparation: Rust may reload/re-broadcast coefficient factors per AVX2 lane block, while DUCC does so per batch. Rust fuses two scalar channels and DUCC maintains plus/minus spin recurrences, and Rust's groups cover physical rings while DUCC packs reflected pairs; they do different work shapes. The existing 2,270 fused-block counter and whole-program Ir totals do not quantify this loop-order cost. Dynamic PC counts normalized by active physical/reflected latitude × degree-pair × channel work are still required.

The exact-GL T320 q8 hemisphere path has a different preparation repeat. Its q8 cache gate prepares scalar coefficient rows once, but each of 16 ring groups copies two `(lmax+2)`-element complex rows into worker scratch for every order, then rebuilds paired recurrence coefficients locally. The copies alone are about 52.9 MB one-way per transform (about 105.8 MB of load+store traffic), source-counted for 16 groups and 321 orders; this excludes paired-factor preparation. The bounded-basis SIMD kernel then writes one degree tile and reads it once for each of two scalar-channel accumulations. That scratch reuse limits live accumulators; removing it could restore register spills. The normal path deliberately keeps this scratch worker-owned. Pinned DUCC 0.42.0 does **not** call `spin1to0` for T320: `alm2leg` uses its normal direct spin recurrence when `lmax < 500`, gathers original E/B coefficients once per order, and runs both components through `inner_loop_a2m`. Therefore the copy/preparation difference is a valid Rust source cost, but the direct DUCC recurrence performs different arithmetic; compare equal active lane-pair and degree work before assigning an instruction premium. The source-matrix DUCC revision `31d9fe99` has the same normal/fast split, but that is the revision used by the 605.134M/226.425M q8 profile, not the pinned production binary.

At the other end, exact GL T720 q8 takes the one-order queue and not the ring-group scheduler. Its existing route stages each order through worker-local Q/U rows: clearing and scattering 721 complex values for each of two channels costs about 33.27 MB of explicit stores per transform. The global spectra were already zeroed. DUCC's parallel layout is m-major behind a transposed view and its `alm2leg` prepares spin-1 scalar coefficients once per order before its inner recurrence, so the staging difference is plausible but not yet an apples-to-apples store-cost comparison.

## Source-only AVX2 comparison for exact GL T720 q8

This is a concrete instruction-count hypothesis, not a measured result. In Rust's accepted GL T720 order-major route, each scalar Q/U pass sees at most 361 reflected northern lanes. `SCALAR_ORDER_BATCH_SIZE=256`, and the ordinary suffix processes two AVX2 vectors per call (`2 * S::F64_LANES = 8` lanes). If the checked prefix reaches ordinary range, a fully active order's two batches therefore traverse the pair loop in at most 32 two-vector chunks for the first 256 lanes, then 13 two-vector chunks plus one final vector for the remaining 105 lanes: at most 46 chunks per component. High-order polar limits reduce this count. Inside each chunk, the degree-pair loop reads the scalar recurrence and even/odd coefficient arrays; `ordinary_two_pair_step_two_vectors` splats each coefficient once and shares it across the two vectors. Source structure therefore permits the same per-degree coefficients to be loaded/broadcast again for each 2-vector chunk; the optimized q8 dynamic PC count is unresolved (`scalar_ordered.rs:962-982, 1122-1248, 2082-2155`).

Pinned DUCC 0.42.0 uses `VLEN=4` for AVX2. On the T720 fast spin-1 route, `alm2leg` applies `spin1to0` once per order and then runs `inner_loop_a2m` for each scalar component. Because `gen.s==0`, that inner loop uses `fill_a2m`, not `fill_a2m_spin`: `nv0=256/VLEN=64`, so each `fill_a2m` batch holds up to 256 compact reflected ring records. `calc_alm2map` then calls `alm2map_kernel`, which loads each degree's coefficient vectors before its `i<nv2` loop and reuses them across up to 64 AVX2 latitude vectors. For T720, `lstep=4096` exceeds the order's degree span, so one recurrence call handles the full degree range per ring-data batch. If all 361 reflected latitude pairs enter the fast route and remain active for an order, DUCC uses at most two 256-record batches per component. The relevant loop nesting differs: Rust's ordinary suffix places the 8-lane chunk loop outside the degree-pair loop, while DUCC places degree outside the `i<nv2` vector loop. Normalized by active SIMD work, both cover 64 vector groups for the first 256 reflected latitude pairs and 27 for the remaining 105 padded to 108: 91 AVX2 vector groups per degree-pair update and scalar component. Rust's 46 helper chunks are 32×2 + 13×2 + 1 vector groups; DUCC's two ring-data batch invocations per component cover 64+27. This does **not** indicate more vector recurrence updates in Rust. The candidate excess is repeated per-degree coefficient loads/broadcasts and chunk-loop overhead: the Rust source splats per two-vector chunk, while DUCC loads coefficient vectors once before its vector-group loop. Actual q8 dynamic counts remain unmeasured; Rust retains recurrence and four sums in registers, while DUCC updates array-backed vector states across larger batches. `rdata_fast`'s sine threshold and order-specific `mlim` can reduce those counts. Register pressure, scratch traffic, cache reuse and LLVM loop transforms must be checked in optimized q8 code before treating repeated splats as removable cost (`sht.cc:190-220, 651-747; sht_inner_loop.h:253-282, 458-545, 1388-1450, 1524-1654`).

A bounded future profile should attribute the coefficient loads/splats and recurrence-state loads/stores separately for the exact q8 adapter, normalize by active reflected-pair × degree-pair × component work, and verify the actual `synthesize_ordinary_suffix_two_vectors` PCs. A possible source-level direction is to reuse coefficient broadcasts across more latitude vectors while retaining only a safe number of live recurrence states; directly widening the current two-vector chunk could spill on AVX2 and is not recommended without disassembly. DUCC's larger batch is an algorithmic reference, not a design to copy blindly.

One tempting redundant operation is already ruled out by prior evidence. The source once placed `cosine * cosine` inside paired loops, but the archived T511 test found the AVX2 compiler had emitted the multiply before the degree-pair loop in both baseline and candidate; static instruction counts matched and moving it in source did not create a repeatable whole-transform gain. Do not repeat that source hoist. The remaining q8 question above is about coefficient-array loads/broadcasts across lane chunks, a separate loop-order mechanism not answered by that earlier disassembly (`archive/experiments/fused-synthesis-register-hoist-2026-10-14.md`).

## Preliminary hypotheses (not production changes or measured rankings)

1. **Exact GL T720 q8 order-local coefficient conversion and validation.** The 16,657,984-byte estimate otherwise satisfies the q8 fused-local-preparation shape but exceeds its gate by 657,984 bytes (4.1%). That existing visitor combines conversion, value safety checks and pair preparation; it could remove the separate row finiteness scan, suffix safety scan and later pair-preparation traversal, although its actual cost is unknown and the threshold may encode a crossover. This fused path was accepted on the distinct CC T720 reduced-q8 workload at 4.18MB, but that result does not establish its crossover at 16.66MB on full GL. It still clears both complete rows first. Independently, the local converter clears 16.66 MB across all orders before overwriting every `m..=lmax+1` slot; the reflected adapter and paired fallback consume only that suffix. A scoped no-clear order-local converter could remove these writes and combine validation while preserving the generic converter contract. Byte/predicate counts have no exclusive Ir or runtime attribution. Any experiment must keep the fallback path and validate poisoned scratch.
2. **Exact GL T720 q8 coefficient broadcasts.** The source layout permits up to 46 Rust 8-lane suffix chunks per component/order versus up to two pinned-DUCC 256-record batches for a fully fast/active order. The existing q8 body disassembly confirms repeated Rust scalar broadcasts and DUCC's pre-loop coefficient-vector loads, but no dynamic PC subtotal isolates their executed cost. It remains a plausible optimization lead, not a supported speedup claim. Reuse across more latitude vectors would expand live recurrence state: the current two-vector path already carries 12 recurrence/accumulator YMM values plus geometry vectors, so a four-vector unroll risks exceeding AVX2's 16 architectural YMM registers. Do not widen or reorder that loop without authorized measurements showing a removable cost and codegen without damaging spills.
3. **Over-resolved GL/CC q8 grouped-route overhead.** The GL T320 over q8 profile has 605.134M Rust versus 226.425M DUCC Ir, and its route counters report 2,270 ordinary fused blocks covering 12.85M lane-pair updates. Source bounds its static schedule to five leaves; CC exact/over-resolved q8 schedules permit at most six leaves. Repeated coefficient conversion and paired-factor preparation are also possible in grouped routes. For GL T320 over specifically, the existing one-order queue is blocked by the cache-geometry predicate requiring exact GL. The scalar-row cache would be 3,287,040 bytes (below the 4,000,000-byte local-conversion cutoff and 34 MiB cache cap); 320 orders produce 40 eligibility tiles, above the q8 threshold of 16. The prepared-component adapter's full-mmax GL predicate already permits the geometry. Existing source-matrix q1 counters report 321 successful adapter orders on both exact and oversampled GL T320; they do not validate q8 order-parallel output or its fallback/reset behavior. The neighboring q1 inlining experiment reduced whole-transform Ir 71% (899.112M→260.816M) but only changed oversampled GL T320 spin-1 elapsed time 39.875→38.159 ms; q8 bypassed that adapter and remained 604.649M→605.134M Ir. This supports testing actual q8 entry into the existing route, while warning that large Ir changes may yield small elapsed gains. A source-level experiment could widen only that cache eligibility, which would select the existing shared coefficient preparation and dynamic order queue, then attempt the checked reflected adapter; declined orders retain the clear-and-fallback path. Successful orders would replace the fused Q/U block kernel and add about 6.55 MB each of worker-row clear and scatter stores. The broadened predicate could also affect larger over-resolved GL q8 cases; scope the first experiment to GL T320 and include GL T511/T1023 controls before generalizing. These competing effects need q8 numerical/adjoint/reset checks, matched Callgrind, worker and whole-transform evidence. This remains an unmeasured candidate with fallbacks; do not prioritize it without exact-route instruction/timing attribution and a compelling reason to grow dispatch complexity.
4. **Exact GL T320 q8 hemisphere preparation and scratch.** The source copies about 52.9 MB of coefficient rows one way, rebuilds pair coefficients across 16 groups, and writes/reloads bounded basis tiles for the two channel passes. DUCC uses direct spin recurrence for T320, so source-level operations differ. Attribute those PCs and normalize recurrence work before extending coefficient caches or changing the tiled basis path.

Lower-priority source checks are the repeated per-batch `power_lower_limit(m)`/`exp` calculation and exact T720's 33.27 MB of Q/U staging stores. In the prepared reflected route, every recorded Q/U component batch dispatches `PreparedComponentBatch::with_simd`, which calls `power_lower_limit(m)`; the route counters report 2,280 such batch calls. The general `ScalarOrderedSynthesis::with_simd` path computes the same order-only threshold once before its latitude-batch loop. Since `m=0` returns before `exp`, the prepared route therefore has 2,276 `exp` calls by source count versus 720 calls if computed once for each nonzero order, or 1,556 duplicate calls. This is a bounded simplification candidate: compute it once for the order and pass it into each prepared component batch. Its whole-transform cost remains unknown. The staging stores also remain below coefficient-row and SIMD-work questions until authorized measurement can show whether they matter (`scalar_ordered.rs:494, 792, 1342; spin_transform.rs:3465, 6012`).

The exact-T720 q1/q8 adapter coverage and ordinary-route work are resolved by existing test-only route counters. Older optimized disassembly classifies one Rust geometry-vector spill and three DUCC coefficient-vector spills; their cache/latency costs are unresolved, and candidate-specific codegen was not needed after the row-clear rejection.
