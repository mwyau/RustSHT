# Independent RustSHT / DUCC0 / SHTns Review

Reviewed 2026-10-15. This report contains static source findings, historical measurement evidence and a proposed implementation sequence. No implementation, compilation, tests, benchmarks or profiling were performed during this review.

## 1. Executive Summary

RustSHT already implements the principal numerical methods needed for competitive spherical harmonic transforms: normalized scaled recurrences, Ishioka paired degrees, polar exclusion, mirrored-ring analysis, scalar conversion for spin 1, fused synthesis kernels and bounded operation-specific Legendre tables. Replacing these algorithms wholesale is unlikely to be the shortest route to DUCC parity. The largest remaining opportunity is the organization of recurrence and accumulation inside analysis, followed by scheduling and synthesis ownership changes that demonstrably remove work. Five discoveries determine the recommended sequence:

1. **Verified source finding — a scalar synthesis overflow guard has incomplete coverage.** In `src/transform.rs:484–505`, transformed-coefficient finiteness is checked only when the T1023 transition path is enabled. Ordinary paired synthesis below that threshold can overflow intermediate coefficients even when the harmonic field is representable. Section 4 gives a concrete T1 analytic case. Correct this before adding another specialized kernel.
2. **Verified source finding — analysis still separates recurrence from reduction at every degree pair.** `ForEachPairedYlm::with_simd` writes recurrence scratch and invokes a visitor, which dispatches another SIMD pass over that basis. DUCC's `map2alm_kernel` advances recurrence and accumulates in the same latitude loop. A bounded fused analysis kernel is the strongest performance experiment, but its speed remains unproven.
3. **Verified source finding — much spin-1 work is already shared.** Production synthesis shares a scalar recurrence between components; analysis shares basis and cosine loads in `AnalysisPairChannelsAccumulation`. DUCC's high-degree spin conversion instead invokes its scalar inner loop separately for the two components. RustSHT therefore has an existing algorithmic advantage that should be retained while removing its remaining recurrence/reducer boundary.
4. **Verified source finding — execution concurrency depends on workspace history.** Recurrence analysis caps its leaf count by scratch allocated when the workspace was constructed. General synthesis also inherits its original ring grouping, with selected exceptions. A workspace constructed in a one-thread pool can remain effectively serial in a larger pool. This behavior is also used deliberately by the existing field-batching experiment; indiscriminate automatic growth would change a measured throughput strategy.
5. **Verified source finding — analysis scheduling recomputes geometric work estimates recursively.** Each candidate order scans all ring cutoffs, twice over much of each recursion node. The split also targets half the work when the child scratch counts differ. A histogram/prefix representation can remove repeated scans without changing the numerical kernel; capacity-proportional splitting addresses non-power-of-two worker counts.

**Previously measured result.** `reports/current-scalar-analysis-kernel-profile-2026-10-14.md`, at Rust revision `5d3ed6b3fd3d8e7d2e3c248d525e91e1e515db62`, reports native reused-workspace scalar T511 analysis at 22.788 ms with one thread and 6.959 ms with eight. Its separately cited Python comparison gives RustSHT/DUCC times of 23.058/6.470 ms and 7.344/1.074 ms. These are different timing boundaries. `reports/spin1-analysis-thread-scaling-2026-10-14.md`, at `772213e349f67c20a3298299134c784ff4fd6bcf`, reports spin-1 analysis scaling from 39.403 to 12.378 ms for RustSHT and 13.056 to 1.943 ms for DUCC between one and eight threads. The DUCC comparisons used package 0.41.0 and the separately pinned reference revision listed below. They establish a historical gap, not current-checkout timings or the cause of that gap. The next implementation session should fix the overflow case, establish an explicit workspace concurrency contract, and prototype scalar analysis fusion. Extend fusion to spin 1 only after scalar measurements justify it. Optimize scheduling metadata independently. Defer order-owned synthesis until simpler changes have been evaluated.

**Verified source finding.** DUCC's `allocate_leg` (`sht.cc:566`) deliberately uses ring-major storage for ordinary analysis, and order-major storage for parallel synthesis or meridional resampling. Therefore the premise that fixed-order analysis must always use a full order-major transpose is not supported by DUCC. RustSHT's successful scalar transpose and unsuccessful spin transpose can coexist without contradiction. The SHTns distinction between precomputed *recurrence factors* and a precomputed *latitude basis* matters. `sht_legendre.c:355–519` constructs recurrence and Ishioka conversion arrays. `sht_init.c:819–934` sets `on_the_fly_only=1` while timing available operation-specific kernels. This checkout does not support recommending large dense basis tables merely because SHTns contains memory-transform names. RustSHT's public plan/workspace design remains appropriate. Its private `ShtScalar` trait separates f32/f64 implementations without exposing a backend hierarchy. The principal maintainability cost is now the number of specialized paths and eligibility conditions, rather than the public API shape.

## 4. Detailed Numerical Algorithm Review

### Scalar synthesis

**Verified source finding.** `src/legendre/scalar.rs:42–83` generates normalized sectoral factors and epsilon coefficients. Sectoral values include the order phase and extended binary scaling. `scalar_paired.rs:25–101` constructs the transformed coefficients and paired recurrence factors corresponding to DUCC `Ylmgen::prepare` (`sht_inner_loop.h:184–205`) and scalar coefficient conversion in `inner_loop_a2m` around line 1539. This optimization is already implemented. `src/transform.rs::synthesize_ring_group` prepares factors per order and latitude group. Eligible blocks reach `synthesize_order_block_partitioned_dispatched` (`scalar_paired.rs:236`) and `FusedSynthesisBlock` (`:1578`). The fused kernel traverses all degree pairs for one SIMD latitude vector, retaining recurrence values and map accumulators in registers at source level. Mixed initial exponents can be partitioned into normal and scaled lanes. Fully excluded blocks are skipped, and selected mixed cutoff blocks are compacted. DUCC uses a different nesting: `alm2map_kernel` (`sht_inner_loop.h:458`) groups two degree pairs, or four in a wide-vector branch, around a latitude-vector loop. It accumulates parity streams and reconstructs mirrored outputs in `extract_a2m`. RustSHT generally synthesizes both hemispheres independently outside its restricted spin-1 specialization. That is a real arithmetic difference, but the previous scalar hemisphere experiment regressed whole-transform time. A useful retry would have to change factor ownership and output organization together.

**Verified source finding — correctness defect.** The check named `paired_coefficients_finite` is assigned `!transition_enabled || check(...)` at `src/transform.rs:498`. Since `SCALAR_TRANSITION_MIN_LMAX=1023`, ordinary lower-degree paired synthesis bypasses this check. The f64 preparation wrapper (`src/legendre/mod.rs:657`) always returns true after writing the transformed streams. `FusedSynthesisBlock` then consumes them without a coefficient finiteness gate. A concrete unexecuted reproducer is f64 scalar GL, `lmax=1`, `mmax=0`, `ntheta=2`, `nphi=1`, `phi0=0`, with `a00=0`, `a10=1.1e308` and real coefficients. The grid and coefficient constraints permit it. Here `epsilon[1]=1/sqrt(3)` and `alpha[0]=sqrt(3)`. Preparing the odd stream multiplies `a10` by `sqrt(3)`, exceeding f64 maximum. The true sampled field is

`a10 * sqrt(3/(4*pi)) * cos(theta) = ±a10/sqrt(4*pi)`,

approximately `±3.10e307`, which is finite. The fused Legendre calculation receives a nonfinite coefficient and produces nonfinite intermediates. This establishes a representable-field failure independently of DUCC behavior. `nphi=1` avoids introducing an unrelated large longitude normalization factor. Confirm the public operation and the internal Fourier result in the next session; no reproducer was run here. The existing T1023 extreme-coefficient regression (`src/transform/tests.rs:397`) specifically exercises the guarded high-degree path. It does not cover this lower-degree branch. The fix should inspect the already prepared streams once per order and use the unpaired scaled recurrence on failure, preserving both ordinary performance and valid extreme inputs.

### Scalar analysis

`analyze_map_to_coefficients` (`src/transform.rs:931`) performs longitude transforms, optional prepared-CC resampling, phase/weight application and an order-major copy using otherwise unused scalar-plan spin buffers. `analyze_symmetric_order_group` (`:1366`) prepares epsilon/paired factors once per order, combines north/south spectra, handles the equatorial singleton, applies independent ring cutoffs and compacts eligible blocks. The remaining hot-loop boundary is explicit. `ForEachPairedYlm::with_simd` (`scalar_paired.rs:2502`) initializes sectoral lanes, calls the visitor for each pair, computes the next recurrence into a slice, swaps slices, and checks whether normalization is needed. The visitor calls `accumulate_analysis_pair_dispatched` (`:1046`). Even the normal path sets up SIMD slices, loads the basis again and horizontally reduces the four parity/component sums. Product eligibility is already checked once per block by `analysis_products_safe` (`:1156`), so recommending its hoist again would be redundant. DUCC's `calc_map2alm` (`sht_inner_loop.h:636`) advances scaled lanes until it can enter `map2alm_kernel` (`:592`). That kernel loads recurrence state, accumulates two paired-degree contributions and advances state within one latitude loop. It does not route each pair through a separate basis-slice callback. Both libraries still require horizontal reduction to produce coefficients; fusion cannot eliminate that mathematical operation.

**Reasoned hypothesis; requires benchmark.** Removing the callback/reducer boundary can reduce repeated basis traffic, dispatch and slice setup. The appropriate target is a fused block kernel with bounded coefficient staging. It is not necessary or realistic to retain all 64 latitude lanes and all coefficients in registers. A small degree panel can retain recurrence values between adjacent updates while keeping Fourier input in cache. Source-level cosine multiplication is not by itself evidence of a generated redundant instruction.

### Spin-1 synthesis

`spin1_to_scalar` (`src/legendre/spin_fast.rs:23`) converts E/B to two scalar streams through degree `L+1`, including the imaginary order coupling and neighboring-degree factors. Synthesis divides their scalar values by `sin(theta)`. DUCC `spin1to0` (`sht.cc:473`) implements the corresponding conversion. The conversion's signs and normalization must remain paired with its transpose; SHTns spheroidal/toroidal coefficients are not interchangeable with these E/B arrays without explicit convention conversion. RustSHT's `synthesize_spin_ring_group_mode` and `synthesize_spin1_scalar_block` (`src/spin_transform.rs:1221,1458`) share basis work between the two streams. The latter checks table eligibility, paired coefficients, polar exclusions, normal kernels and scaled fallbacks. The scalar-conversion latitude threshold is `1e-4`; the paired specialization has a stricter `1e-2` threshold. General spin recurrence remains necessary at poles and outside eligible modes. Production also contains parallel scalar-coefficient preparation (`prepare_spin1_scalar_coefficients`, `:1065`), bounded by 17 MiB and L≤720 on eligible q≥8 GL synthesis. The rows are rebuilt for every call because coefficients can change. Current source uses the shared T15 scalar-conversion lower bound in this gate; the earlier cache report's T127 lower-bound description is not the complete current selector. Selected full-band exact GL T319–T511, q4–q8 operations use `spin_transform/hemisphere.rs::is_beneficial`. The staged transition path already combines `(even + odd*cos(theta))*basis` with guarded scaled multiplication (`scalar_paired.rs::StagedSynthesisPairTransition`). The accepted factorization report records its advantage. Cached-row copies and repeated pair preparation remain visible, but the direct-read experiment did not establish a gain and pair preparation had negligible historical instruction attribution. Neither deserves another isolated retry. DERIV1 is implemented through degree normalization and an eligible scalar-conversion route; GRAD_ONLY can omit the B input. Exact analysis and adjoint analysis remain STANDARD. New STANDARD kernels should leave unsupported modes on their established paths until separately validated.

### Spin-1 analysis

`analyze_spin_order_group` (`src/spin_transform.rs:2168`) distinguishes weighted GL/prepared-grid analysis from unweighted synthesis adjoints. The GL paired path (`:2612`) weights Q/U by ring weight, inverse sine and, when applicable, longitude normalization. North and south cutoffs are checked independently; the singleton equator is not counted twice. It accumulates scalar streams, reverses the paired-degree coefficient transformation, then applies `scalar_to_spin1` (`spin_fast.rs:105`). `accumulate_spin_scalar_analysis_pair_block` (`spin_transform.rs:2522`) advances the basis once and calls `accumulate_analysis_pair_channels_dispatched` (`scalar_paired.rs:1114`). When both channel inputs and recurrence are safe, one SIMD pass loads shared basis/cosine vectors and reduces Q/U simultaneously. Otherwise the established per-channel mixed/scaled reducers remain available. Full GL paired-order fallback stages contributions in worker arrays and commits E/B only after success; a late unsafe block does not first commit half an order. DUCC `leg2alm_internal` (`sht.cc:878–917`) uses one generator per worker/order but calls `inner_loop_m2a` separately for each scalar component. RustSHT already avoids that repeated basis generation on its shared path. Its residual cost comes from materialized recurrence state, per-pair callback/reducer dispatch and guarded mixed-range work. Replacing scalar conversion with direct spin recurrence would discard an established advantage.

### Correctness observations across operators

**Verified source finding.** `HarmonicSpec::validate_coefficients` (`src/harmonics.rs:113`) enforces packed length, real `m=0` and zero coefficients below spin. It does not implement a blanket finite-input rejection. Map analysis likewise has no general NaN/Inf scan. Table/product guards exclude unsafe inputs from particular fast paths, but they are not a universal input-validation contract. NaN/Inf behavior should be documented and regression-tested; allowing IEEE propagation is not itself a numerical defect. The finite-input overflow above is a separate issue. Scalar synthesis allows the real even-longitude Nyquist order and doubles its real contribution after phase application (`src/transform.rs:768–775`). Exact analysis rejects that order with `(nphi-1)/2`; synthesis adjoints have their own contract. Keep these distinctions and the real harmonic inner product with weight two for `m>0`. Roundtrips alone cannot validate them. GL construction uses Newton iteration through 100 nodes and Bogaert above (`src/grid.rs:359–448,519`). DUCC uses `long double` in its small-grid Newton branch (`gl_integrator.cc:38–77`); Rust uses f64. This is a known bounded precision difference with recorded node/weight tests, not a new defect or a high-resolution bottleneck. CC/F1 exact analysis uses reflected meridional profiles with sign `(-1)^(m+spin)`, F1 phase shifts, spectral resizing and weighted prepared-CC projection (`src/meridional.rs::to_prepared`, `restore_original`). This matches the operator composition in DUCC `analysis_2d` around `sht.cc:1761–1798` and its adjoint. Shared kernel changes must preserve endpoint weights and the distinction between the original and prepared geometries. Direct low-resolution quadrature is not an acceptable substitute.

f32 uses separate scalar/spin recurrences and defaults out of paired/table specializations (`src/legendre/mod.rs:89,1252`). f64 speedups therefore do not imply f32 speedups. Spin 2 retains its scalar-conversion and direct fallbacks; spins 3/4 depend on the general spin path and shared orchestration. Their existing supported cases must remain covered.

## 5. SIMD and Data-Movement Analysis

**Verified source finding.** The recurrence arrays in `ForEachPairedYlm` are read/written separately from the reducer's basis reads. The normal recurrence also revisits lane-range checks each degree pair. DUCC separates its scaled transition from the ordinary kernel; SHTns separates high-degree scaling behavior and uses degree panels. RustSHT's extra checks protect its wider input/fallback behavior, so removing them without a proof would trade away correctness. The bounded fusion experiment should retain a per-block product guard, stage coefficient increments in O(L) worker scratch and commit only after successful completion. If a late vector or scalar tail needs scaling, discard the staged increments and rerun that block through the existing callback path. This makes fallback transactional. Do not update the public coefficient output incrementally and then replay the entire block. A first scalar prototype should integrate recurrence and reduction under one Pulp dispatch while limiting live accumulators. Compare one degree pair with a two-pair panel only after the first works. Preserve the current reduction structure initially where practical. More unrolling is not automatically useful: the accepted scalar reducer already uses two independent vector chains, and the third-chain experiment introduced register pressure and regressed time. Spin 1 has eight component/parity sums before recurrence state, making its register budget tighter. There are meaningful existing layout choices to preserve:

- Scalar analysis combines transpose, phase and quadrature weighting once, with already allocated workspace storage (`transform.rs:1001–1054`).
- Spin analysis prepares short structure-of-arrays blocks from ring-major input. Its rejected full transpose added 8 MiB at T511 and 15.864 MiB at T720 and slowed warm q8 execution, as recorded in `reports/spin1-analysis-thread-scaling-2026-10-14.md`.
- The compact table stores `(order, degree offset, north latitude)` contiguously, reconstructing south values by parity (`scalar_table.rs:173–344`). Its payload bound and lazy `OnceLock` initialization are already implemented. Warm-table timing must remain separate from construction cost.
- Synthesis factor generation repeats across latitude groups. DUCC's order ownership eliminates that repetition; a Rust order-owned design could do the same, but requires a different writable Fourier layout and a bounded conversion back to longitude rows. DUCC also precomputes cosine squared in `fill_a2m`/`fill_m2a`, using `(1-sin(theta))*(1+sin(theta))` near the poles. Rust commonly forms cosine squared inside recurrence source. The earlier synthesis assembly study found the compiler already hoisted that multiply. The polar expression is a numerical difference worth retaining in high-degree sensitivity tests; no current accuracy failure has been established from it. Avoid large factor/basis caches as a default response. SHTns precomputes O(L²) factors, whereas Rust's general recurrence storage is O(L) per scratch slot plus Fourier planes. A new factor cache exchanges repeated square roots for memory footprint and cache traffic. Existing factor-cache and direct-read failures provide no basis for making that trade globally.

## 6. Parallel Scaling Analysis

### Work partitioning and ownership

`analyze_order_groups_parallel` (`src/transform.rs:1243`) and its spin equivalent (`src/spin_transform.rs:3506`) recursively split contiguous packed coefficient slices with `split_at_mut`. Scratch is split alongside output. Rayon may steal recursive tasks, but after the final leaves are formed there is normally no queue of additional order work for a finished worker. Each order has a single owner and requires no coefficient reduction across workers. DUCC uses `execDynamic(nm,nthreads,1)` in both transform directions (`sht.cc:684,729,878,922`). The scheduler claims chunks through an atomic counter (`infra/threading.cc:576–580`); worker-local generator and temporary coefficient arrays persist while it obtains further orders. SHTns's `omp_spat_to_SH.gen.c:75–101` similarly schedules individual orders dynamically. Its synthesis template also exposes an order/batch loop. Dynamic scheduling has overhead and is not proof of superior performance on every workload.

### Explainable imbalance

Rust's estimator multiplies degree count by active ring count (`transform.rs:77–111`). It does not distinguish normal, mixed-exponent and scaled recurrence lanes; compaction tails; spin fast-range versus polar work; conversion setup; or cache locality. Source paths have materially different costs. Thus nearly equal estimated work can plausibly yield unequal leaf duration. Which factor dominates requires path counts and timing.

**Previously measured result.** `reports/spin1-analysis-leaf-overpartition-2026-10-14.md` reports earlier 1.5–2.8× leaf-time variation. Doubling leaves regressed T511 q8 by a median paired 3.19% and T720 q8 by 11.55%. The q16 result was inconsistent. A simple extra-leaf policy is already rejected. The separate constant-overhead weight adjustment in `spin1-analysis-thread-scaling-2026-10-14.md` was also inconclusive. Two smaller structural issues can be addressed first. The current active-ring splitter repeatedly scans all N ring limits for each order at each recursion level: approximately O(M N log p) estimator work for M orders and p leaves. A cutoff histogram, suffix active counts and prefix work sums reduce construction to O(N+M), followed by small split searches. Preserve the existing estimator first to isolate this change. Second, the splitter targets equal work but assigns `ceil(p/2)` scratch slots left and `floor(p/2)` right. At p=3, one side gets half the estimated work for one slot while the other half is divided between two. The same asymmetry appears inside p=6. Power-of-two benchmarks miss it.

### Workspace history and concurrency policy

`ShtWorkspace::new` (`src/workspace.rs:238–274`) derives ring grouping and analysis scratch capacity from the construction pool. Analysis later uses `min(current_threads, scratch_count, orders)` (`transform.rs:1075–1080`; `spin_transform.rs:687–692`) without growing that capacity. General synthesis uses the saved grouping. The special exact-GL fine-group selector (`plan.rs:314`) and hemisphere path are exceptions, not a general adaptation mechanism. A recurrence-only T1023 workspace created at q1 has one scratch group. Moving it to q8 leaves analysis at one leaf; general synthesis also has one group outside the fine-group window. This is a verified scheduling consequence, not a numerical race. It cannot explain the quoted baseline gap where workspaces were constructed for each benchmark pool. Crucially, `examples/m5_batch_bench.rs:276–285` deliberately constructs one-thread workspaces for concurrent fields, and its report records useful throughput. Do not silently turn every such workspace into a full-pool operation. Document the effective execution budget and offer an explicit way to prepare a workspace for a different pool/budget, with coherent synthesis grouping and analysis capacity. Preserve intentional field-level concurrency and memory bounds. Tests must cover both directions of pool migration and this batching use.

### Serial stages, cache and NUMA

Longitude rows run serially around the Legendre stage (`transform.rs:352,948`; spin orchestration has analogous loops). Scalar transpose/weighting and CC/F1 meridional order loops also contribute serial work. They impose an Amdahl limit, but existing instruction profiles cannot quantify that limit in elapsed time. Instrument these boundaries later; FFT engine work remains outside this plan. Workspace vectors are initialized on the constructing thread, and recursive leaves own scratch independently of the physical worker that eventually executes them. Cache reuse, placement across CCDs, first-touch pages and contention are plausible contributors to q8/q16 behavior. No inspected evidence proves NUMA saturation, false sharing or a specific cache bottleneck. Future measurements must record actual CPU topology/affinity instead of assuming CPU IDs 0–7 represent a particular placement. No mutable scratch sharing was found in the inspected native parallel kernels. Their disjoint slices provide ownership without locks or unsafe pointer arithmetic. Python has a separate per-plan workspace mutex (`python/src/lib.rs:23–30,662`), so concurrent calls on one Python plan serialize by design. That boundary should not be confused with native intra-transform scaling.

## 7. SHTns Techniques Worth Borrowing

**Verified source finding.** SHTns supplies useful design comparisons, not a replacement module to port:

| Technique and evidence | Relevance to RustSHT |
|---|---|
| Fused degree panels, `SHT/kernel_spat_to_SH.gen.c:45–56,477–575` | Use a small number of Pulp panel variants; select only measured winners. Scalar/vector degree spans differ because register needs differ. |
| Vector conversion helpers, `sht_private.h:300,527`; kernel synthesis lines 218–240 | Confirms scalar conversion is a practical vector-transform strategy. Rust already shares two channels; preserve its E/B conventions and fallback. |
| Dynamic order ownership, OpenMP templates | Useful for a later scheduler/synthesis redesign after measuring path-dependent imbalance. Do not repeat the failed two-leaf policy unchanged. |
| Per-operation function selection, `sht_init.c::choose_best_sht` | Rust already has deterministic operation-specific selection. Borrow the comparison discipline; avoid hidden constructor timing. |
| Recurrence factors prepared with configuration, `sht_legendre.c:355–519` | A possible bounded setup trade, but broad O(L²) caching needs evidence beyond arithmetic counts. |
| Order-local inner batch iteration, `omp_SH_to_spat.gen.c:99–117` | Shows cache-aware batching without proving basis reuse across fields. Rust's existing field-concurrency strategy remains the measured option. |
| Scalar m=0 mean extraction, `kernel_spat_to_SH.gen.c:97–115` | Useful for investigating leakage from a large constant background into tiny higher modes; no Rust accuracy failure or performance gain is established. |

SHTns uses north/south symmetry, SIMD latitude lanes, polar exclusion and scaled high-degree recurrence, all already represented in RustSHT. Its `PolarOptimize` (`sht_init.c:572`) determines cutoffs from a caller threshold and maximum basis magnitude. Rust's DUCC-derived cutoff rule is different; adopting more aggressive SHTns thresholds would change scientific error behavior and is not recommended. The generated templates contain ISA-dependent unrolling and explicit restrictions. `sht_fly.c` disables some large `NWAY` combinations with comments about accuracy on wide vectors. The lesson is to validate each panel/ISA combination, not infer AVX-512 correctness or speed from AVX2. This review did not build SHTns or establish which generated variant a particular installation executes. Its `sht_auto` maps to a Gaussian grid (`sht_init.c:1405`); its grid names are not a substitute for Rust's CC/F1 exact-analysis contract.

## 8. Findings and Risks

| Rank | Finding | Severity / confidence | Evidence and qualification |
|---|---|---|---|
| F1 | Low-degree paired synthesis can overflow transformed coefficients for a finite representable field | Correctness: high; source confidence: high | `transform.rs:484–519`, `scalar_paired.rs:63–101,1578`; analytic T1 construction in section 4. Runtime reproducer pending. |
| F2 | Recurrence/reducer boundary remains in scalar and spin-1 analysis | Performance opportunity: high; structural confidence: high; speed confidence: medium | `scalar_paired.rs:2502`, `transform.rs:1470–1528`, `spin_transform.rs:2522`; DUCC `map2alm_kernel`. Historical profile supports prioritization. |
| F3 | Workspace construction can cap later recurrence parallelism; selectors use the executing pool | Performance/API clarity: medium; confidence: high | `workspace.rs:238–274`, analysis worker-count sites, `plan.rs:73,259`. Intentional small workspaces are also used for batching. |
| F4 | Work estimates are rescanned; equal-work splits ignore unequal child capacities | Scheduling efficiency: medium; confidence: high | `transform.rs:77–111,1274–1295`, `spin_transform.rs:3550–3582`. Elapsed impact unmeasured; odd worker counts need coverage. |
| F5 | Synthesis latitude ownership repeats factor/conversion work and often both hemispheres | Architectural opportunity: medium/high; confidence in net benefit: low | `transform.rs:457`, `spin_transform.rs:1221`, versus DUCC `alm2leg` and SHTns order kernels. Earlier pairing/caching failures constrain a retry. |
| F6 | Specialized-path correctness and dispatch are spread across large modules | Maintenance risk: medium; confidence: high | Multiple thresholds in `spin_transform.rs`, `plan.rs`, `scalar_table.rs`; transactional fallback conventions vary by kernel. Centralize eligibility documentation while touching each path. |

No additional race or unsafe-memory defect was established in the inspected native ownership paths. Missing performance evidence should not be converted into a safety finding. Conversely, tests for one fast path do not establish the safety of another: the T1 guard gap demonstrates why boundary-specific regressions are necessary.

## 9. Prioritized Optimization Roadmap

Six principal recommendations follow. Impact is qualitative and workload-dependent. None is a predicted speedup percentage.

| ID / priority | Action | Expected impact | Effort | Numerical risk | Confidence |
|---|---|---|---|---|---|
| R1 / P0 | Cover every paired-synthesis entry with safe coefficient preparation | High correctness impact; ordinary-speed impact should be small | Small | Low/medium | High: explicit failing arithmetic |
| R2 / P0 | Make workspace execution capacity explicit and support deliberate pool changes | High for affected migrated workspaces; no explanation of matched-pool baseline gap | Medium | Low | High structural finding; policy must preserve batching |
| R3 / P1 | Fuse scalar analysis recurrence and reduction with transactional block staging | Potentially high at T255–T2047 | Medium | Medium | High mechanism confidence; requires benchmark |
| R4 / P1 | Extend accepted analysis fusion to shared spin-1 channels | Potentially high at T511–T2047 | Medium/large | Medium/high | Medium; AVX2 register pressure is a material risk |
| R5 / P1 | Build work prefixes once; split by child capacity; measure residual imbalance | Low/medium for prefix work; potentially medium for awkward pool sizes | Small/medium | Low | High work-removal confidence; elapsed impact unknown |
| R6 / P2 | Prototype order-owned synthesis with bounded Fourier layout conversion | Potentially high for parallel high-degree synthesis | Large | Medium/high | Low net-speed confidence until measured |

R1 uses existing unpaired scaled fallback. R2 must distinguish allocation capacity from deliberate execution budget. R3/R4 preserve f32, polar, unsafe-product and unsupported-mode fallbacks. R5 initially preserves the existing order cost model and summation order. R6 retains the current latitude-group implementation as its default until whole-transform evidence supports a restricted selector. For R3, the exact reference is DUCC `sht_inner_loop.h::map2alm_kernel`; for R4 it is that fused scalar mechanism combined with Rust's existing two-channel sharing, rather than DUCC's duplicate component calls. R5 compares Rust's recursive split with DUCC's dynamic order queue and SHTns's dynamic OpenMP loop. R6 combines DUCC order ownership with SHTns's conversion-once-per-order organization; it is not a simple repetition of the rejected hemisphere experiment.

Open questions require bounded evidence:

- Does scalar fusion save enough traffic and dispatch to pay for coefficient staging and range guards on current AVX2 code? R3 answers this directly.
- Does joint spin-1 fusion fit the register budget, or is the existing shared reducer already the better decomposition? R4 must compare against current production.
- How much leaf-time variation comes from mixed/scaled work versus scheduling, placement or shared-host noise? Record path counts and worker duration together before changing the scheduler.
- How large is serial orchestration in native elapsed time after kernel improvements? Existing instruction profiles cannot answer this, and this review does not authorize FFT internals work.
- Would m=0 mean removal or DUCC's polar cosine-squared expression improve accuracy in a demonstrated difficult field? Add diagnostic accuracy cases first; neither is an established Rust defect.
- Should explicit workspace execution capacity be part of the public API or a narrower preparation method? The concrete requirements are deliberate pool adaptation, preserved batch concurrency and bounded allocation.
- Are immutable geometry caches worthwhile after eliminating repeated scheduling scans? They could remove repeated trigonometry/cutoff setup, but those O(N) operations should not distract from the O(L²N) kernel without phase evidence.

## 13. Final Recommendation

Fix the scalar paired-coefficient overflow gap first. Document and test workspace concurrency before changing its adaptation behavior. Then implement one bounded scalar analysis fusion prototype with transactional fallback and compare it against the current callback kernel at q1 and q8 before broadening the matrix. Retain the accepted spin-1 scalar-conversion, shared-Q/U, compact-table and hemisphere specializations. Extend analysis fusion to spin 1 only after evidence supports the scalar mechanism. Simplify scheduling estimates independently, including non-power-of-two pools. Defer dynamic scheduling and order-owned synthesis until refreshed measurements show which remaining cost they would remove. The evidence supports targeted changes to hot-loop organization and work ownership. It does not support a numerical rewrite, larger dense tables, more aggressive cutoffs or an unconditional claim that copying DUCC or SHTns architecture will close the performance gap.
