# RustSHT agent instructions

**Only active implementation plan:** [plans/11-ducc-equivalent-scalar-analysis.md](plans/11-ducc-equivalent-scalar-analysis.md). Its current primary objective is to **close the measured approximately 2× scalar-analysis gap with DUCC**, not to end a campaign after isolated small improvements.
Read that plan and the current production source before acting. Explicit current owner instructions take precedence. Other plans, old reviews, handoffs and benchmark reports are **historical evidence or numerical references**, not competing agent goals. Do not preload them.

- **Scope:** investigate the *actual executed SIMD assembly and runtime hotspots* for `opt/sht-performance-parity`. Close the attributable Rust/DUCC analysis gap through evidence-led structural improvements, not a succession of unconnected 2–5% tweaks. Keep experiments isolated for attribution; larger redesigns are allowed when the matched bottleneck and rejected-approach history justify them. No unrelated FFT work, broad campaigns or new dependencies.
- **Numerics:** preserve the Rust API, independent `S/A/S*/A*` operators, GL/CC/F1, f32/f64, spin 0–4, correct scaling/phase/weights, subnormal and extreme-value safeguards, SIMD tails, serial/parallel behavior and checked fallbacks. Verify against pinned DUCC **and** analytic/adjoint tests; never relax tolerances for speed.
- **Implementation:** stable Rust, portable runtime Pulp SIMD and bounded caller-owned scratch. Neutral RustSHT source names, correct GPL-2.0-or-later and translated DUCC attribution. Archive demonstrably retired prototypes; do not retain layers of competing kernels.
- **Evidence:** compare **equivalent kernel boundaries and actual executed SIMD machine code** using matched native Rust/DUCC release builds. Isolate normal versus scaled work, hot-loop frequency, memory access, reductions, checks, loads/stores, compiler effects and full-transform overhead. A shorter assembly listing or lower stack frame is not proof of speed. Keep investigating the dominant residual when an isolated small change succeeds. No arbitrary truncation-specific or percentage acceptance target. Preserve historical evidence; keep raw disassembly and local host/process/PSI logs untracked, with concise reproducible findings committed.
- **Benchmark repetitions:** Nine single-call samples are insufficient for final Rust/DUCC claims. For authoritative comparisons, warm up and calibrate repeated kernel invocations to ~20–100 ms per timed batch; collect **at least 30 batches across multiple independent runs** per case, pin single-threaded trials to one physical CPU core, interleave Rust/DUCC runs, and report median, p10/p90 and raw spread. Keep equivalent work/reset semantics; label shorter exploratory screens provisional and investigate distinct timing regimes before declaring parity or regression.
- **Workflow:** at most one Luna benchmark-only subagent, no Sol reviewer unless the owner changes this. Run formatting, relevant Clippy, release tests and no-default-features tests, with Python tests if bindings change.
- **Reviewable progress:** For the cumulative DUCC-parity campaign, implement and benchmark one change at a time; make small, buildable, numerically validated commits and push after each meaningful change, following the sync rule below. Keep correct-but-slower experiments for the final combined 64/128/256-lane evaluation and ablation; label them experimental, record results concisely in `PERFORMANCE_STATUS.md`, and continue after pushing. Never push known correctness regressions.
- **Mandatory sync before every push:** inspect worktree; commit/stash uncommitted work safely; `git fetch origin`; **rebase only unpublished local commits onto `origin/opt/sht-performance-parity`** using `git rebase origin/opt/sht-performance-parity` (a no-op if already current). Resolve conflicts without losing concurrent work; if unsafe, preserve local work and report the conflict rather than resetting or force-pushing. After rebasing, reread the latest `AGENTS.md`, `plans/11-ducc-equivalent-scalar-analysis.md` and any newly changed owner instructions; rerun affected tests; normal push and verify remote HEAD. **After every pull, rebase, merge or other remote integration, check the latest instructions again before continuing work.** Do not rewrite already-published commits, force-push or touch `main` without authorization.
